The eco-cycle

Every feature is a loop through one shared document. A screen calls the api client → a Fastify endpoint mutates the Itinerary (insert-only / non-destructive) → the write lands in Firestore → the client's edits store bumps a version → useAsync refetches → the screen (and the map behind it) updates. That single spine is why add-a-stop shows on the Day and the map, why a settled expense appears in Alerts, and why a shared companion sees the same trip.

v2.0.0

Map-first 3D redesign

Requested. Match app-preview.html exactly (the night, map-first design); make the map a real Google-style 3D map; fix the "AJAX error" on map screens; and take the walking mannequin off the map.

Prerequisites & what was added

  • Night theme pinned — theme.ts returns the dark palette always; tokens aligned 1:1 to the design.
  • MapFirst shell — the dark sheet + live map every screen renders through.
  • Vector basemap — OpenFreeMap dark (keyless) so buildings have geometry to extrude into 3D.
  • MapLibre worker fix (required) — vector tiles need the worker; under Metro its URL 404'd (the AJAXError). Copied it into public/ + setWorkerUrl. Without this the map is blank — a hard disconnection.
  • Road/building occlusion + rotation; mannequin removed from the map.

Why this direction

The map isn't a widget here — it's the app's spine, so it had to be fixed first. Real 3D buildings are impossible on raster tiles (no geometry), and vector tiles were the only free path — which made the worker a hidden hard-dependency, not an optional extra.

Pinning the theme at the token layer meant one change reskinned every screen connects → all screens, avoiding per-screen drift.

Home itinerary switcher

Requested. "Where do we see the other itineraries on Home? We should be able to slide to see them."

Prerequisites & what was added

  • Load all trips up-front — Home fetches every itinerary (not just list[0]) so switching is instant.
  • Swipeable roster — a horizontal card row; the active trip is state.
  • Reuses MapFirst's stops/route — selecting a trip feeds new pins + route to the same map (no new map code).

Why this direction

Home had collapsed to one trip during the redesign. Preloading all trips trades a few fetches at open-time for zero-latency switching — the right call for a small trip count.

The switcher didn't need new map plumbing: MapFirst already reacts to its stops, so the selection just changes the data feeding it connects → MapFirst (v2.0).

v2.3.0

Add-a-stop (non-destructive)

Requested. Add Star City to Sat Sep 12 in an already-sorted itinerary — "how do we make sure the plan still goes well?"

Prerequisites & what was added

  • Activity.added flag (additive type) — marks user stops as editable/removable.
  • Insert-only endpoints — POST/DELETE …/activities; the server sorts by time, preserves ownerId, and refuses to delete originals.
  • lib/geocode.ts (Nominatim) for the new stop's map coords.
  • Reactive edits store (required) — markStale() → useEditsVersion() makes the Day refetch after adding; without it the new stop would save but never show — a silent disconnection.

Why this direction

The worry was destruction, so non-destructiveness is enforced in the server, not just promised: insert-only, originals protected, sample ownership preserved.

The reactive store is the connective tissue: it lets a write on the Add screen surface on the Day and the map connects → Day + map (v2.0). This same store later powers expenses, members and reimbursements.

v2.4.0

Expense ledger + receipt OCR

Requested. Screenshot a receipt → the app reads it → itemized + total, per person, paid/unpaid → see the receipt + items → total unpaid for the week/month (sort & filter) → settle in one go.

Prerequisites & what was added

  • Expense types + Itinerary.expenses — the ledger lives on the trip document (naturally scoped, migrates cleanly).
  • chatVisionJson — a vision call reusing the existing OpenAI client → the OCR endpoint POST /receipts/parse.
  • Image downscale — receipts are shrunk client-side so the OCR payload + stored thumbnail stay small.
  • Stale-while-revalidate fix (required) — useAsync keeps data during refetch, else marking one expense paid flashed a full-screen spinner. Fixes Day too.

Why this direction

OCR didn't need a new service — the OpenAI key was already wired for trip generation, so a vision variant was the cheap path. Expenses on the itinerary doc means the same read/refetch loop as everything else connects → edits store (v2.3).

Money never moves through the app — it records and (v2.6) proves — so no payment rail or KYC, matching "take the screenshot as proof."

v2.5.0

Dynamic sharing & companions

Requested. Don't hardcode "sister-in-law" — ask "who else should know this trip?" and make it a dynamic way of adding people.

Prerequisites & what was added

  • Member / Share types + Itinerary.members/shares — one roster of anyone (any relation, viewer/editor).
  • Member CRUD + share create/delete; a public GET /shared/:token read-only view.
  • Token embeds the itinerary id (<id>~<uuid>) — resolves without a global scan, so no new repo method.
  • Payers made dynamic (removed a disconnection) — Add-expense chips now come from the roster, not a hardcoded array.

Why this direction

People are a hub, not a fixed enum. Modelling a roster means sharing, expense payers, and later split-party all pull from one list connects → expenses (v2.4).

Encoding the trip id in the token sidesteps the auth/index work a global share-lookup would need — the read stays public and O(1).

v2.6.0

Proof + e-signature + notifications

Requested. Reimburse in one go, upload a screenshot as proof, require a signature authorising the transfer, and notify whoever was paid.

Prerequisites & what was added

  • Reimbursement/Signature types + Itinerary.reimbursements + Expense.reimbursementId — a settled batch is its own record, linked to the expenses it cleared.
  • SignaturePad — draw → SVG data URL (portable, cross-platform); Settle screen adds proof upload.
  • Alerts wired to reimbursement events (the notification) — settling posts "Reimbursed ₱X to {payer}" into the Alerts feed.
  • Firestore ignoreUndefinedProperties (required) — optional fields (no memberId/proof/note) were 500-ing the write; the fix protects every endpoint.
  • Void reverts a reimbursement to unpaid — reversible like the rest.

Why this direction

"Notify whomever" needed a real channel — so Alerts stopped being mock data and started reading reimbursement events connects → Alerts. The settle → record → Alerts path closes the loop end-to-end.

The signature is stored as an SVG so it's small, sharp at any size, and works on web and native without a canvas-export dependency.

v2.7.0

Google Places cost reference

Requested. Before turning on Google Places, know exactly what it costs — per place, per itinerary, what re-charges on revisit, what we pull vs. the full menu — as a local HTML we can open from Settings.

Prerequisites & what was added

  • public/places-cost.html — an interactive calculator + the SKU menu, built on the real cost model in server/places/google.ts (details $0.020–0.025, photo $0.007, reviews $0.025) and our current field mask.
  • Settings entry — Profile → "Google Places cost" opens it via Linking.openURL(origin + '/places-cost.html').
  • No API change — this is a planning reference; the crawl itself stays off until the toggle is flipped.

Why this direction

Cost visibility before spend: the page makes the three buckets explicit — facts (cached once, $0 on revisit), photos (lazy, ~1h reuse), reviews (never stored, on-demand). It reads the same numbers the server bills at, so the estimate can't drift from the code connects → server/places/google.ts.

Kept as a local file opened from Settings (not an app screen or a hosted artifact) so it's a quick internal reference we can update as Google's pricing moves.
